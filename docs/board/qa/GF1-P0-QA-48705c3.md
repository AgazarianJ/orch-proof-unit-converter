## 4. Evaluator integrity

### 4.1 Test glob: can a new `test/*.test.mjs` change the evaluator's behaviour?

**Globals and monkeypatching: not possible.** On Node 22, `node --test` runs each test file in its own child process (default `--test-isolation=process`).
- Experiment E1: a sibling `test/aaa-patch.test.mjs` replaced `globalThis.fetch` and set `process.env.SMOKE_ATTEMPTS=0`.
- `scaffold.test.mjs` was unaffected: 5 passed, 0 failed.
- `smoke.mjs` and `build.mjs` also run as further child processes with a fresh environment taken from the scaffold process.

**Tampering with locked files on disk: possible (F-1, MAJOR).** A new test file can rewrite a locked file at runtime, even though the diff never touches it. Node runs test files concurrently, and `scaffold.test.mjs` spawns `scripts/build.mjs` and `scripts/smoke.mjs` from disk while its tests run.

Experiment E2:
- E2a: the marker was removed from `app/index.html`. Without tampering, `npm test` correctly failed (3 passed, 1 failed).
- E2b: same broken app, plus a new `test/aaa-tamper.test.mjs` that overwrites `scripts/build.mjs` at import time with a build that always emits the marker.
- Result of E2b: `npm test` gave **`fail 0` in 5 of 5 runs**, so the locked build test was defeated deterministically.
- The `ci` job's later `npm run build` step also uses the tampered file, so the whole `ci` check goes green.
- A PR diff containing only `app/index.html` and a new test file would pass the Board's "no locked files touched" diff check.

Rewriting `test/scaffold.test.mjs` itself is a race. It lost in our single run, but it may win on a loaded runner.

Impact and mitigation:
- Only the pre-merge `ci` gate is affected.
- `deploy` and `hosted-smoke` use fresh checkouts and never run `test/*`, so after merge `hosted-smoke` would still catch a missing marker. By then, though, the broken commit is on `main` and live.
- Because `.github/**` and the scripts are locked forever after this package, the fix has to land now.

**Smallest hardening (ci.yml only):** run the locked checks before any non-locked code runs, then prove the tracked tree was not mutated.

```yaml
      - run: node --test test/scaffold.test.mjs   # locked evaluator first, before any untrusted test code runs
      - run: npm run build
      - run: npm test                             # all tests, including future ones
      - run: git diff --exit-code && test -z "$(git status --porcelain --untracked-files=no)"
```

Add `timeout-minutes: 15` to the job as well (F-4).

Optional additional step: the Board's acceptance gate should also diff later PRs against the locked list. CI cannot enforce the lock by itself, because a `pull_request` run uses the PR's own copy of `ci.yml`.

### 4.2 Build determinism and version provenance

- Two builds with the same `GITHUB_SHA` produced byte-identical `dist/` (sha256 of `index.html` and `version.json` matched).
- The build does no network access, writes no timestamps and does not depend on directory ordering.
- `dist/version.json` is always written by `build.mjs` **after** `cp(app → dist)`.
  - Experiment E3: a forged `app/version.json` containing `{"sha":"forged"}` was overwritten with the real SHA. App code cannot forge the version.
  - No test covers this, see F-6.
- In `deploy`, `GITHUB_SHA` is set explicitly to `${{ github.sha }}`. That is the pushed `main` commit, and for a merge it is the merge commit. `hosted-smoke` compares against the same `${{ github.sha }}` within the same run.
- `GITHUB_SHA ?? 'local'`: if the variable were ever unset, `version.json` would read `local` and `hosted-smoke` would fail. That failure direction is safe.

Weakness (F-2, MINOR): `cp` copies symlinks as symlinks, and `upload-pages-artifact` archives with `tar --dereference --hard-dereference`.
- E3: `app/leak.txt -> ../package.json` became a symlink to an absolute path in `dist/`.
- Consequence: an `app/` symlink to any file readable on the runner would be published publicly on Pages.
- The repository has no secrets, but app code could still pull files from outside `app/` into the deployed site.

### 4.3 Does `hosted-smoke` require the exact merge commit?

| Threat | Behaviour | Verdict |
| --- | --- | --- |
| Stale deploy (old `version.json`) | strict `version?.sha !== expectedSha` → retry, then fail | ✅ blocked (also covered by a test) |
| Near-miss sha (trailing space, uppercase, prefix, array wrapper) | all fail (own negatives) | ✅ |
| Whitespace or pretty-printed JSON around a correct sha | passes, which is correct: the value is compared, not the bytes | ✅ |
| CDN / HTTP cache | unique `?t=<ms>-<random>` query on both URLs, plus `cache: 'no-store'`, `cache-control: no-cache`, `pragma: no-cache` | ✅ |
| 404 page containing the marker | `res.ok` check → fail (own negative) | ✅ blocked, **no test** (F-6) |
| `version.json` with a non-2xx status | fail (own negative) | ✅ |
| Redirect | `fetch` follows redirects; a 302 to a page with the marker passed (own negative) | ⚠️ F-3. App code cannot create HTTP redirects on Pages, so this is not exploitable from `app/**` |
| `index.html` from a different deploy than `version.json` | both are fetched in the same attempt; Pages deploys are atomic | acceptable |
| Retries pass after a transient stale response | yes, by design (the stale-then-fresh negative passed) | ✅ expected |

Retry bounds:
- Default: 20 attempts with 15 s between them, which is about 5 minutes when the server answers fast.
- Worst case, with every fetch hitting the 30 s timeout: 20 × (2 × 30 s + 15 s) ≈ 25 min. That is well inside GitHub's 6 h job limit.
- The script always terminates. Invalid `SMOKE_*` values exit with code 2. `SMOKE_ATTEMPTS=0` is clamped to 1 attempt and still fails. An unreachable host exits with code 1.
- No `SMOKE_*` variables are set in the workflow, and repository variables are unused.
- No job sets `timeout-minutes` (F-4).

### 4.4 Other influence paths from app code

- `workflow_dispatch` on `deploy` accepts any ref, so a user with write access can dispatch it from a feature branch and publish unmerged code (F-7).
  - The `github-pages` environment's deployment-branch policy, which is a repository setting not visible in code, may already prevent this.
  - Whether or not it does, `hosted-smoke` would pass for that branch SHA. A green `deploy` run therefore does not prove that `main` was deployed unless its head branch is `main`.
- Concurrency keeps at most one pending run per group. If several pushes land while a deploy is running, the intermediate runs are cancelled rather than queued. A cancelled run is not a pass, and the Board must not treat it as one.
